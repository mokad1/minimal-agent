# 架构设计题（问答）

---

## 模块一 · Context / Performance

### Q：一个 session 连续聊了 200 轮，context 快爆了，你会怎么做压缩？如何确保压缩后的对话仍然流畅？

分三段处理，提前动手，不要等塞不下了再压。

最近十轮左右原样保留。用户说"那个""上面那个"都要靠最近几轮的具体内容才能听懂，工具调用和工具结果也必须成对留着。

再往前的一段，把老对话和上一版总结一起交给模型，重新写一段总结。

最早的部分只留几条固定信息：用户是谁、有什么硬性要求、还有哪些事没做完、已经定下的结论。这几条单独存，不参与压缩。因为让模型自己总结，总结几次就会走样，原话是"周五前发"，可能变成"这周内"。

工具返回的内容通常很长，一次搜索几千字。总结时只留标题和一句结论，不要把原文抄进去。

被压缩掉的原话另外存到文件里，总结里留个编号，用户追问细节时再按关键词找回来。

保证流畅有两个要点。一是总结放在系统提示里，不要放在用户消息里，否则模型会把它当成刚下的命令。二是最近几轮完整保留，压缩只动老消息。

总结里一定要写清现在在做什么、还有什么事没做完，不然模型会忘记目标。

## 模块二 · Memory

### Q：和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题，Agent 如何做 memory 召回更合理？

关键在存，不在找。当时那段对话如果没有存成以后能找到的样子，后面找得再准也没用。

记忆分四类存。一类是用户的基本情况，比如职业、习惯、用什么技术。一类是过去的提问和回答，带日期。一类是从对话里总结出的结论。一类是还没做完的事。

不是每句话都存。只存不会变的信息和完整的问答，闲聊和"现在几点"这种不存，否则很快就全是垃圾。

找的时候三个办法一起用。按意思找相近的，按名字找关键词（人名、项目名这类词按意思找不准），再按时间远近打分，越久远的越靠后。同时优先用用户自己说的，模型自己猜的不太可靠。

后来知道的新情况覆盖旧的，但旧的留着并记上有效期，用户问"之前不是用 MySQL 吗"就能答出来。

找到的内容不要整段塞给模型。压成三到五条，写明是什么时候说的、谁说的，比如"用户 9 月 12 日说：数据库已经换成 PostgreSQL"。写上日期，模型才能判断这条信息是不是过时了，要不要先跟用户确认。

不够像的内容就不要拿出来，每次最多给五条。

## 模块三 · Task

### Q：对于长程任务，大模型执行一段时间可能会忘掉目标，有哪些解决方案，各有什么优缺点？

做法都一样：不要指望模型自己记住，把目标放在对话外面。

每次重新说一遍目标。简单省事，但占篇幅，模型还是可能不理。

把计划写进文件或者待办工具里，每轮读回来。可靠，中断了能接着做，缺点是模型得主动去写，写着写着格式会乱。

把大任务拆成小步，每步都有明确的完成标准。不容易一路错到底，但拆得对不对本身是个问题。

定期把进度记下来：做完什么、还剩什么、有什么不能碰。程序崩了能恢复，代价是多花点篇幅。

由程序控制流程，模型只负责每一步怎么做。最不容易跑偏，但不够灵活，遇到没预料的情况就卡住。

隔几步问模型一次"目标是什么、做到哪了"。实现简单，但多一次调用，而且模型可能骗自己说已经做完了。

实际是组合用：计划和进度存在外面，每步验收，每换一个阶段把目标重说一遍。存的内容大概是"目标、当前阶段、已完成、待完成、不能违反的条件"。

## 模块四 · Tool / Session Runtime

### Q：如果 session state 为 busy，此时用户又发来新消息，或者异步工具完成事件也到达，runtime 应该如何处理？

原则三条：同一个会话同一时间只能有一处在改，事情不能丢，出问题能恢复。给会话加锁，任何时候只允许一个流程在改对话记录，否则两边同时改一定乱。

用户发新消息有三种处理。排到后面等：先记下来，等当前这轮跑完再处理，适合长任务。打断：等当前这次模型调用结束就停，不能强行中断正在跑的工具，适合聊天。合并：新消息只是补充说明，直接并到当前这轮里。

工具跑完的结果不能直接写进对话记录，因为模型可能正在发请求。应该先放进这个会话的待办队列，记上编号和时间。等当前这轮结束的时候取出来处理。如果会话已经空闲了，结果一到达就直接启动新一轮处理，不需要用户再说话。

还要补几件事：结果要存到磁盘，程序重启不能丢；每条结果带编号，同一条重复到达只处理一次；同一个会话按顺序处理；工具要有超时，用户取消后结果又回来了就丢掉不用；对话记录带版本号，写之前先比对，变过就重新读一遍再写。

## 模块五 · Agent Runtime 架构对比

### Q：Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？各自设计的优缺点是什么？

区别在于"要调用工具"这件事记在消息的哪个位置。

Claude Code 用的格式，是把工具调用当成消息内容的一部分放进去：

```json
{"role": "assistant", "content": [
  {"type": "text", "text": "我查一下"},
  {"type": "tool_use", "id": "toolu_1", "name": "weather", "input": {"city": "北京"}}
]}
{"role": "user", "content": [
  {"type": "tool_result", "tool_use_id": "toolu_1", "content": "晴 25°C", "is_error": false}
]}
```

OpenAI 这种格式，是把工具调用单独列成一个字段，结果再单独发一条消息：

```json
{"role": "assistant", "content": "我查一下",
 "tool_calls": [{"id": "call_1", "type": "function",
                 "function": {"name": "weather", "arguments": "{\"city\":\"北京\"}"}}]}
{"role": "tool", "tool_call_id": "call_1", "content": "晴 25°C"}
```

主要区别有四个。

参数怎么给。前者直接就是一个字典，后者是一段字符串，得自己解析，而且边传边收的时候还要拼起来。

先后顺序。前者说话和调工具在同一个列表里，谁先谁后很清楚；后者是两个分开的字段，模型"先说一句再调工具"的顺序就丢了。

出错怎么表示。前者有专门的错误标记，一看就知道工具失败了；后者只能约定好在文字里写"错误：..."。

一次调多个工具。前者要求所有结果一次性放在同一条消息里返回，不容易漏；后者每个结果单独一条消息，可以先给一个后给一个。

前一种更严谨，但实现麻烦，支持的模型也少。后一种简单、哪个平台都能用，代价是参数容易解析失败、错误只能靠文字判断，所以接的时候一定要做容错，解析不了也别让程序崩。
